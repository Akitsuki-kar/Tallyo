1. 配置与构建

P0 ECharts 全量引入导致 Stats chunk 达 1MB+

位置： src/composables/useECharts.ts:13

import * as echarts from 'echarts' 将完整 ECharts 包（~1MB）打入 Stats 路由 chunk。构建产物 Stats-*.js 达 1,045KB（gzip 347KB），移动端首屏进入统计页需下载近半兆 JS。

修复方案：改用按需引入：

// 仅引入折线图、柱状图、饼图 + 必要组件
import { use } from 'echarts/core';
import { LineChart, BarChart, PieChart } from 'echarts/charts';
import { GridComponent, TooltipComponent, LegendComponent, TitleComponent } from 'echarts/components';
import { CanvasRenderer } from 'echarts/renderers';

use([LineChart, BarChart, PieChart, GridComponent, TooltipComponent, LegendComponent, TitleComponent, CanvasRenderer]);

预计 Stats chunk 可从 1,045KB 降至 ~200KB（gzip ~70KB）。

影响：移动端首屏性能 · 工作量：~30min
P1 @rollup/plugin-babel 幽灵依赖

位置： package.json dependencies

@rollup/plugin-babel 列在 dependencies 中但项目源码从未 import。它是 jspdf / workbox-build 的间接依赖，不应作为项目直接依赖。应从 dependencies 中删除。

影响：依赖膨胀 · 工作量：~2min
P1 emptyOutDir: false 临时 workaround 未清理

位置： vite.config.ts:12

注释标注"避免批量删除触发沙箱安全保护"，项目记忆中也标记为"最终交付前改回 true"。当前仍为 false，导致 dist/ 中可能残留旧版本文件（本次构建即有 199 个文件，部分可能是旧产物）。

影响：部署产物可能包含过期文件 · 工作量：~1min
P1 无 ESLint / Prettier / 单元测试

项目无任何 .eslintrc、.prettierrc 配置文件，src 下无任何 *.test.ts / *.spec.ts。readingChain.ts、pricing.ts、merge.ts 都是纯函数且注释中提到"可 esbuild 编译跑断言"，但实际未落地为持久化测试。

建议：至少为核心纯函数补测：readingChain（findPreviousReading / relinkChain）、pricing（calcTieredCost / calcCost）、merge（resolveLWW / mergeEntities）。

影响：回归风险 · 工作量：~2h（核心纯函数测试）
P1 PWA precache 体积过大（14.8MB）

Workbox globPatterns 缓存了全部 **/*.{js,css,html,svg,png,ico,woff2}，precache 列表 200 条共 14.8MB。其中 html2canvas（201KB）和 jspdf（357KB）已被正确拆为独立 chunk 并动态 import，但 precache 仍会预缓存它们——用户可能永远不用 PDF 导出却被迫下载。

建议：在 workbox 配置中用 globIgnores 排除 html2canvas/jspdf chunk，或使用 maximumFileSizeToCacheInBytes 限制。

影响：首次安装下载量 · 工作量：~10min

2. 数据层与 Store 架构

P1 getReadingsByPremiseMonth 全量扫描后 JS 过滤

位置： src/db/repositories/readingRepo.ts:36-39

该函数先通过 getAllFromIndex('readings', 'premiseId', premiseId) 取出该房源所有读数，再在 JS 中 filter(r => r.date.startsWith(yearMonth))。对于长期使用积累了数百条读数的房源，每次账单 recompute 都全量读取再过滤。

建议：创建复合索引 ['premiseId', 'date'] 或 ['premiseId', 'type', 'date']，使用 IDB keyRange 直接定位月度数据。需要 DB_VERSION 升级 + 迁移回调。

影响：大数据量性能 · 工作量：~1h（含 DB 迁移）
P1 增量扫描函数未利用 syncVersion 索引

位置： 各 repo 的 getDirtyXxxSince(since) 函数

schema.ts 中已为所有 store 创建了 syncVersion 索引，但 getDirtyReadingsSince 等函数都是 getAllReadings().filter(r => r.syncVersion > since)——先全量再过滤，索引形同虚设。虽然当前同步走全量快照（D5 决策），这些增量接口暂未使用，但留着不用反而误导。

建议：改用 db.getAllFromIndex('readings', 'syncVersion') + keyRange，或删除未使用的增量接口避免混淆。

影响：代码整洁度 · 工作量：~30min
P1 无 IndexedDB 版本迁移策略

位置： src/db/schema.ts DB_VERSION = 1

createStores 用 if (!db.objectStoreNames.contains()) 做了存在性判断，这在全新安装时正确。但一旦未来需要加索引或改字段（如上面的复合索引），需要在 upgrade 回调中按版本分支处理，当前完全没有版本迁移的骨架。

建议：预留 if (oldVersion < 2) { ... } 的迁移骨架注释。

影响：未来可维护性 · 工作量：~15min（骨架预留）

3. 核心业务逻辑

P0 defaultView 设置已保存但从未接线使用

位置： src/stores/settings.ts + src/main.ts + src/router/index.ts

用户可在设置页选择"默认视图"（首页/读数/账单/统计/预算），settings store 正确保存了该值。但 main.ts 的 bootstrap() 从未读取 defaultView 并执行路由跳转，router 也始终以 '/' 为起点。该功能是半成品。

修复方案：在 bootstrap() 末尾加：

if (settings.defaultView && settings.defaultView !== 'home') {
  router.replace({ name: settings.defaultView });
}

或在 router 的 beforeEach 守卫中处理首次进入。

影响：用户设置无效 · 工作量：~15min
P1 recomputeAll 笛卡尔积遍历

位置： src/stores/bills.ts:132-146

recomputeAll 遍历所有 premises × 所有 months 的笛卡尔积。但实际上某月可能只在部分房源有读数，不需要对所有组合执行 recompute。当有 5 套房源 × 12 个月 = 60 次 recompute，每次都触发 IndexedDB 查询 + 账单写入判断。

建议：按 (premiseId, monthKey) 组合去重后再遍历，而非 premises × months 笛卡尔积。

影响：同步后全量重算性能 · 工作量：~20min
P1 月度账单仅取月末最后一条读数

位置： src/stores/bills.ts:87-90

账单计算取该月最后一条读数的 reading - previousReading 作为用量。如果用户一个月内录了多条读数（如月初1000、月中1050、月末1100），账单只反映 1050→1100 的差值（50），而非整月用量（100）。

这是设计选择而非 bug——表读数天然如此，用户每月录一条即可。但应在 UI 上明确提示"按最近一次读数计算用量"，避免用户误解。

影响：用户理解 · 工作量：~10min（加提示文案）
P1 数据导入无 LWW 合并，直接覆盖

位置： src/utils/dataExport.ts:47-54

importData 调用 applySnapshot(snapshot)，而 applySnapshot 内部是"远端胜出实体逐个 putRepo"——相当于直接覆盖本地。如果用户在导入前有未同步的本地编辑，这些编辑会被导入文件直接覆盖，没有 LWW 裁决。

建议：导入前先 buildLocalSnapshot 取本地数据，与导入数据做 mergeSnapshotDetailed 合并后再 apply。

影响：数据安全 · 工作量：~30min

4. 同步机制

P1 同步锁存在竞态条件

位置： src/sync/lock.ts:53-61

acquireLock 先 readLock() 读锁状态，判断无锁后 writeLock() 写入。这两步之间不是原子操作——如果两个 tab 几乎同时调用，都可能读到 null 并都获取锁。虽然单设备场景概率极低（需毫秒级并发），但技术上存在。

建议：使用 BroadcastChannel + leader election 替代 localStorage 锁，或在 acquireLock 中写入后读回验证 token 是否匹配。

影响：多 tab 并发同步 · 工作量：~1h
P1 无 schemaVersion 迁移路径

位置： src/sync/snapshot.ts:115

parseRemoteSnapshot 严格校验 schemaVersion === 1，不匹配则抛错。一旦未来需要升级 schema（如加字段、改结构），没有降级/迁移路径，旧版客户端拉到新 schema 会直接报错。

建议：预留 if (obj.schemaVersion > SCHEMA_VERSION) { /* 提示用户升级 */ } 和 if (obj.schemaVersion < SCHEMA_VERSION) { /* 迁移 */ } 分支。

影响：版本升级 · 工作量：~30min（骨架）

5. UI 组件与体验

P1 无 prefers-color-scheme 自动主题

主题切换仅支持手动 light/dark，CSS 中无 @media (prefers-color-scheme: dark) 自动跟随系统。用户如果系统设为深色但 App 为浅色，体验割裂。

建议：在 Settings 增加"跟随系统"选项（theme: 'auto'），在 useTheme 中监听 matchMedia('(prefers-color-scheme: dark)')。

影响：用户体验 · 工作量：~40min
P1 Google Fonts CDN 在离线 PWA 中不可用

index.html 从 fonts.googleapis.com 加载 Caveat 字体，Service Worker 不缓存该外部请求。离线时字体回退到圆体（--sdb-font-rounded），虽 font-display:swap 已做渐进增强，但首次在线加载时也会产生额外网络请求（FOUT）。

建议：将 Caveat 字体文件本地化到 public/fonts/，在 CSS 中 @font-face 引用，并纳入 SW 缓存。或接受当前回退方案（hero 数字仅装饰性）。

影响：离线体验 · 工作量：~20min
P1 7 个 Tab 在小屏可能拥挤

位置： src/components/common/AppTabBar.vue

底部导航 7 个 tab（首页/读数/账单/统计/预算/设置/同步），在 360px 窄屏上每项仅 ~51px，图标 21px + 文字 11px 紧凑排列。sync 可能可以考虑合并到 Settings 中作为入口。

建议：将"同步"入口移入设置页（设置页已有"数据同步"入口），底部 Tab 精简为 6 个。

影响：移动端可用性 · 工作量：~15min
P2 无加载骨架屏 / 组件错误边界

各页面 onMounted 中 await store.load() 期间无加载骨架屏，仅显示空白或空状态组件。组件级错误无 onErrorCaptured 兜底，异常会导致白屏。

影响：体验 · 工作量：~1h

6. 性能

P1 bootstrap 预加载全部 store

位置： src/main.ts:34-55

bootstrap() 在应用启动时同步等待 6 个 store 全部 load() 完成后才挂载。其中 readings.load() 和 bills.load() 需要全量读取 IndexedDB。对于积累大量数据的用户，启动会有可感知延迟。

建议：settings + premises 必须先加载（决定布局），readings/bills/prices/budgets 可改为路由级懒加载。

影响：启动速度 · 工作量：~1h
P2 PDF 分页偏移逻辑有潜在 bug

位置： src/utils/pdf.ts:66-72

多页 PDF 的 addImage(imgData, 'JPEG', margin, margin - position, imgWidth, imgHeight) 中 position 累加 pageContentHeight，但 imgHeight 是完整图片高度。jsPDF 对超出当前页的内容不会自动裁剪，而是依赖 Y 轴偏移让超出部分"滚"出可视区域——这在某些 jsPDF 版本中可能产生空白页或内容截断。

建议：改用 canvas 分段裁剪方式：将源 canvas 按页高切分为多个子 canvas，逐页 addImage。

影响：长账单 PDF 导出 · 工作量：~40min

7. 安全

P1 无 CSP (Content Security Policy)

index.html 和 vite.config.ts 中无 CSP meta 或 header。虽然当前无外部脚本注入风险（Vant、Vue 均为本地打包），但缺少 CSP 是安全最佳实践的缺漏。特别是 Google Fonts 外部请求，若 CDN 被劫持可注入恶意 CSS。

建议：添加 <meta http-equiv="Content-Security-Policy" content="default-src 'self'; style-src 'self' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: blob:;">

影响：安全加固 · 工作量：~15min

8. 可扩展方向

  • 燃气/热力表支持：ReadingType 加 'gas'，PriceConfig 和 Bill 扩展 gas 字段，UI 类型选项增加。当前类型系统设计为联合类型，扩展成本低。
  • 年度汇总报表：按年聚合月度账单，生成年度费用趋势 + 月均/年均对比。Stats 页已有月度维度图表，加一个年度切换即可。
  • 读数搜索：ReadingList 加按日期/备注搜索。当前 filter 仅支持 premiseId/type/month，可加 text 搜索。
  • CSV/Excel 导出：dataExport.ts 复用 buildLocalSnapshot，将读数/账单展平为表格格式导出。
  • 读数提醒通知：PWA Notification API + Push，月底提醒用户录读数。useAutoSync 已有 online 监听基础。
  • 在线/离线状态指示器：useAutoSync 已监听 online/offline 事件，但 UI 无展示。可在 AppHeader 加一个小图标。
  • 多账单日周期：当前按自然月，可扩展"账单日"（如每月5号为周期）。monthKeyFromDate 改为按自定义周期计算。
  • 数据删除/清理：当前仅软删（墓碑），无硬删/清理过期墓碑的入口。可加"清理已删除数据"功能（调用各 repo 的 deleteXxxHard）。
  • 年度对比图表：Stats 页加"同比"指标（今年 vs 去年同期），deltaTone 逻辑已具备 up/down 判定基础。
